01 / OVERVIEW

How an Agent Processes a Request

STAGE 01
transcript.py

Data Acquisition

User provides raw input. The Tool layer validates it, fetches real-world data from an external source, normalizes it into clean text, and handles fallbacks if the source fails.

→
STAGE 02
prompts.py

Prompt Assembly

The Knowledge layer selects the right prompt template, injects the style modifier and the fetched data as variables, and returns a complete system + user prompt pair.

→
STAGE 03
agent.py

Intelligence

The Brain layer sends the assembled prompt to the LLM, handles authentication and rate-limit errors gracefully, and returns the generated output as a clean string.

→
STAGE 04
database.py

Memory

The Memory layer optionally persists the result with metadata. If no database is configured, this step silently skips — the agent works regardless. History and analytics are enhancements, not dependencies.

03 / DEEP DIVE

Four Lessons, Four Layers

01
The Brain Layer
agent.py

The heart of any agent. Every LLM integration follows the same four patterns regardless of which model you use.

The Brain layer is where the LLM call lives. It is deliberately thin — it does not make decisions about what to generate or how to structure prompts. Its sole job is to receive a ready-to-send prompt package and return a clean string. This separation is what makes the same Brain layer work across LinkedIn posts, clinical summaries, and coding assistants.

Client Initialization

Always abstract your API connection into a function that is called once. It checks deployment secrets first, falls back to local environment variables second. This single pattern makes the same codebase work on your laptop and in the cloud without any changes.

The Core LLM Call Shape

Every LLM call follows an identical structure: build the prompt, call the model with a system and user message, extract the content field from the response, return a string. This shape never changes. What changes is the prompt — and that belongs in the Knowledge layer, not here.

Key Insight

The content_type and style parameters are how one function serves six different outputs. The logic for each lives in prompts.py — the Brain layer never needs to know what it is generating.

Structured Output from LLM

When you need the model to return data rather than prose, you must explicitly instruct it to return only valid JSON with no markdown fences or preamble. Before parsing, always strip any code fence characters the model may have added. Always have a safe fallback in the error handler so a parsing failure never crashes the UI.

Typed Error Handling

Do not catch all errors the same way. Classify them — invalid API key, rate limit exceeded, network timeout — and return a descriptive string for each. The UI layer can then check whether the output begins with "Error:" and display an appropriate message rather than showing a raw exception.

02
The Knowledge Layer
prompts.py

Where the agent's intelligence actually lives. Not in the model — in the prompts.

The Knowledge layer is the most powerful file in any agent. The LLM model is generic — it knows everything about everything. Prompts.py is what makes it a specialist. A content agent, a clinical coder, a radiology summariser — the model is the same; the prompts are entirely different.

Separate Data from Logic

The file is organized into three pure data dictionaries followed by two pure functions. Nothing mixes. The dictionaries hold all prompt text. The functions assemble and return prompt pairs. Adding a new output format means adding one dictionary entry — zero changes anywhere else in the codebase.

System vs User Prompt

These are two distinct things with two distinct jobs. The system prompt sets the AI's persona and expertise — it is static and does not change between calls. The user prompt contains the actual task, the constraints, and the input data — it is dynamically constructed for every call.

Rule of Thumb

System prompt = who the AI is right now. User prompt = what to do with this specific input. Never mix them.

Template Variables

User prompts contain placeholders — slots for the style instruction and the input data. A single assembly function fills these placeholders at runtime using Python's built-in string formatting. This is how one template serves millions of different inputs without duplication.

The Cross-Cutting Modifier

A writing style (Viral, Educational, Founder, Technical) is stored as a single instruction string. That string is injected into every content type prompt as a variable. When the user changes the style, all six outputs shift in tone simultaneously. This pattern is directly transferable to clinical settings: patient-facing vs physician-facing vs billing mode works identically.

The Most Important Prompt Rule

Always tell the model what not to include. Without negative constraints, LLMs prepend preamble phrases like "Here is your LinkedIn post:" before every output, which breaks downstream parsing. Negative instructions are as important as positive ones — often more so.

03
The Tool Layer
transcript.py

The most important architectural pattern in agentic AI. How an agent interacts with the outside world.

The Tool layer is where agents cross boundaries. A tool is any function that touches something outside the agent itself — an external API, a file system, a database, the web. The critical principle: the LLM never makes external calls directly. The Tool does. The Tool normalizes the result. Only then does the cleaned data reach the Brain.

Validate Before Any Network Call

Never send bad input to an external API. Validate the input with a regex or schema check first. If it fails, return an error dictionary immediately. This is called failing fast — you save a network round trip and give the user a specific, actionable error message instead of a cryptic API exception.

Consistent Return Schema

Every single return path from a tool — success, partial success, every type of failure — should return the same shape of data. A dictionary with a predictable set of keys. The caller only checks one thing: is there an "error" key? If yes, display it. If no, proceed with the data.

Fallback Chains

Real-world APIs fail. Design every tool with Strategy 1 → Strategy 2 → Strategy 3 before giving up. When multiple strategies exist, prefer quality over speed. Document the fallback chain explicitly so future developers know the intent.

Critical Real-World Pattern

Always normalize data before passing to the LLM. Raw API responses are noisy, inconsistent, and full of metadata the model does not need. The Tool's job is to return clean, plain text — never raw API output.

Context Window Management

Long documents can exceed the LLM's token limit. Every tool that processes variable-length input needs a chunking strategy. The most practical approach: keep the beginning and the end — where the most informative content typically lives — and trim the middle with an explicit marker showing what was removed.

Optional Dependencies

Some tools rely on heavy libraries that should not be required for the agent to function at all. Import these inside the function, not at the top of the file. Catch all exceptions and return safe defaults.

04
The Memory Layer
database.py

Persistence across sessions. Transforms a single-use tool into a system with history, analytics, and accountability.

Without memory, an agent processes each request in isolation and forgets everything. The Memory layer gives it persistence — the ability to accumulate history, surface patterns, and build analytics over time. In healthcare, this is the difference between a one-time tool and an auditable clinical workflow system.

Memory is Optional, Not a Dependency

The agent must work perfectly whether or not a database is configured. Every database function checks whether a connection exists before doing anything. If not, it returns a safe default — an empty list, a zero count, a sentinel integer. The UI never crashes because of a missing database.

Cache Expensive Connections

Creating a database client is slow. Create it once and reuse it across all subsequent calls in the same session. Never instantiate a new database connection on every function call. In frameworks with caching decorators, use them explicitly.

Separate Reads from Writes

One function per operation. Write functions save data and return a confirmation. Read functions query data — and different read functions select different subsets of columns depending on what the caller needs. Never fetch more data than the caller will use.

Always Return Safe Defaults

Every function that returns a collection or aggregate should return an empty structure on failure — never null, never an exception. An empty list. A dictionary with all counts set to zero. This means the UI layer can always safely access any field in the return value without defensive coding at every call site.

The Schema Principle

One well-designed table handles all content types when they share the same shape. A table with input_id, input_type, output_type, output_text, metadata, created_at serves every use case. In healthcare: note_id, note_type, output_type, processed_text, metadata, created_at.

05 / PRINCIPLES

Eight Design Principles

⚡
Single Responsibility
Each file does exactly one thing. Responsibilities never bleed across files. This is what makes agents maintainable and extendable.
🛡️
Graceful Degradation
The core function always works. Optional components silently skip when unavailable. Never let infrastructure break the agent.
🧱
Data Over Logic
Add new output formats as data entries, not new code paths. The logic layer stays fixed; only the data dictionary grows.
🔒
Validate First
Never call an external API with unvalidated input. Fail fast, return a specific error, save the network round trip.
🌊
Fallback Chains
Real APIs fail. Design every tool with Strategy 1 → 2 → 3. Prefer quality over speed when multiple strategies exist.
✂️
Context Management
Long inputs must be chunked before hitting the LLM. Keep start and end; trim the middle. Every doc-processing agent needs this.
📐
Consistent Schema
Every return path returns the same shape. One key to check for errors. The UI never needs defensive coding.
🔁
Cache Connections
Create database and API clients once; reuse them. Never instantiate a new connection on every function call.
06 / APPLICATION

Mapping to Healthcare AI

The architecture is domain-agnostic. The same 5 layers that power a content repurposing agent power a clinical note processing agent. Only the data in each layer changes — never the structure.

The Universal Insight

The code structure of a clinical AI agent is nearly identical to the content repurposing agent described in this article. Replace "YouTube URL" with "clinical note" and "LinkedIn post" with "billing suggestion" — the pipeline is identical. The domain changes. The architecture does not.

07 / ROADMAP

What to Build Next

Easy

Extend the Existing Architecture

  • Add new output types as data entries — no code changes needed
  • Batch-process multiple inputs from a folder or list
  • Detect input language and generate output in the same language
  • Add more writing style modifiers to the style library
Intermediate

Add New Capabilities

  • Connect to external posting APIs (Buffer, LinkedIn) from the Tool layer
  • Add UI controls for tone, length, and formality as sliders
  • Generate image prompts alongside each output
  • Build a feedback loop that improves prompts based on user ratings
Advanced

Production-Grade Systems

  • Use embeddings to cluster past outputs by topic or semantic similarity
  • A/B test prompt variants and track performance with analytics
  • Build a multi-agent system where specialized sub-agents collaborate
  • Add RAG pipelines to ground outputs in verified domain knowledge
