Section 01 · Retrieval-Augmented Generation

1RAG: Access Knowledge at Query Time

RAG solves the knowledge scale problem. When your information is vast, dynamic, and constantly evolving, like every medical journal published this week, every hospital policy update, and every patient lab result from yesterday, you cannot fit it into a model's context window. You have to retrieve it, on demand, at the exact moment it is needed.

Core Definition

Retrieval-Augmented Generation (RAG)

An architecture where the LLM queries an external knowledge base (vector DB, SQL, document store) at inference time, retrieves the most relevant chunks, and uses them as grounded context to generate its answer. The model never memorizes the knowledge. It looks it up every single time.

Query → Retrieve(top-k) → Augment(prompt) → Generate

How RAG Works, Step by Step

  • Indexing phase (offline): Documents (PDFs, EHR notes, guidelines) are chunked, embedded into vectors via a model like text-embedding-3-large, and stored in a vector database (Pinecone, Weaviate, Qdrant, pgvector).
  • Query phase (online): The user's question is embedded using the same model, then compared against the vector store using cosine similarity or ANN search.
  • Retrieval: The top-k most semantically similar chunks are fetched (typically 3–10 chunks).
  • Augmentation: These chunks are injected into the LLM prompt as context, alongside the user's question.
  • Generation: The LLM produces an answer grounded in the retrieved evidence, often with citations.
Figure 1.1 · RAG pipeline: the query is embedded, retrieved from the vector store, and fed to the LLM as context.

Key Characteristics of RAG

Massive Scale

Can reach millions of documents: entire medical libraries, decades of patient records, regulatory filings.

Always Current

Just update the underlying database. No retraining, no cache invalidation. Yesterday's published study is available today.

Citable & Auditable

Every answer can be traced back to a specific source document, which is critical for clinical accountability and compliance.

Oncology Clinical Decision Support High Complexity

Clinical Decision Support for Rare Cancers

Dr. Chen, Medical Oncologist · 9:14 AM · Before rounds

A 58-year-old patient has been diagnosed with Philadelphia chromosome-like acute lymphoblastic leukemia (Ph-like ALL) carrying a JAK2 V617F mutation. The patient is also on amlodipine for hypertension and has mild renal impairment (eGFR 52). Dr. Chen needs to know:

  • What are the latest second-line targeted therapies for this specific mutation?
  • Are there drug-drug interactions with amlodipine via CYP3A4 pathways?
  • What dose adjustments are required for renal impairment?
  • Are there any active clinical trials at our institution?
What are the latest second-line treatment protocols for Ph-like ALL with JAK2 V617F, and how do they interact with amlodipine in a patient with eGFR 52?
RAG in action: The system queries PubMed (last 90 days), the hospital's oncology protocol library, the pharmacy interaction database (Micromedex), and the clinical trials registry. It retrieves 7 relevant chunks: a 2025 NEJM trial on ruxolitinib in Ph-like ALL, a drug interaction alert for CYP3A4 substrates, a renal dosing guideline, and 2 active Phase II trials at the hospital. The LLM synthesizes a cited recommendation.

Why RAG is essential here

  • Oncology knowledge changes weekly: new trials, new approvals.
  • The answer requires cross-referencing several dynamic databases at once.
  • A static cache would be outdated before the patient's next appointment.

Tradeoffs & Risks

✓ Strengths
  • Scales to unlimited knowledge
  • Always uses the latest information
  • Answers are citable and auditable
  • No retraining required for updates
  • Works across heterogeneous data sources
✕ Risks
  • Retrieval latency (100–800ms extra)
  • Wrong retrieval means a wrong answer
  • Requires high-quality embeddings and metadata
  • Chunking strategy is critical and non-trivial
  • Vector DB infrastructure cost at scale
"RAG is the right answer when your knowledge is too large, too dynamic, or too distributed to fit in any context window, and when being wrong is more dangerous than being slow."
Section 02 · Cache-Augmented Generation

2CAG: Cache Knowledge for Instant Recall

CAG solves the latency problem. When your knowledge is stable, bounded, and has to be accessed in milliseconds rather than hundreds of milliseconds, you pre-load it directly into the model's context via a precomputed KV cache. There is no retrieval step. The knowledge is already there, waiting.

Core Definition

Cache-Augmented Generation (CAG)

An architecture where all relevant knowledge is loaded into the LLM's context window upfront, and the resulting Key-Value (KV) cache is precomputed and stored. At inference time, the model skips retrieval entirely and simply continues generation from the cached context. Latency for the knowledge-access portion drops from hundreds of milliseconds to single-digit milliseconds.

Precompute: Documents → KV Cache → Store
Inference: Query + Cached KV → Generate (instant)

How CAG Works, Step by Step

  • Offline preparation: A bounded set of documents (say, a 200-page protocol manual) is loaded into the model's context. The model performs a forward pass, and the resulting KV cache (the internal attention states) is serialized to disk or memory.
  • Cache storage: The KV cache is held in fast memory (GPU VRAM, Redis, or a dedicated cache server). It can be swapped in and out as needed.
  • Online inference: When a user asks a question, the cached KV is loaded (or already resident), and the model generates an answer by attending to the pre-loaded knowledge. No embedding, no similarity search, no retrieval.
  • Cache invalidation: When the underlying knowledge changes, the cache must be rebuilt. This is the critical operational constraint of CAG.
Figure 2.1 · CAG pipeline: knowledge is pre-loaded into the KV cache offline; inference is retrieval-free and near-instant.

Key Characteristics of CAG

Ultra-Low Latency

Removes the retrieval round-trip entirely. Critical for time-sensitive clinical scenarios.

Deterministic Access

No risk of retrieving the wrong chunk. The model already holds the full, authoritative document in context.

Simpler Infrastructure

No vector DB, no embedding pipeline, no retrieval tuning. Just a cached model and a fast inference server.

Emergency Trauma Bay Mission-Critical Latency

ER Trauma Resuscitation Co-Pilot

Trauma Team Lead · Bay 3 · 2:47 AM · Penetrating chest injury

A 34-year-old male arrives via EMS with a stab wound to the left chest. Blood pressure is 78/40, O₂ saturation is dropping to 84% on a non-rebreather, and the trachea is deviated to the right. The trauma team lead needs instant, authoritative guidance, not in 500ms but in under 100ms, because every second counts.

Patient with penetrating left chest trauma, hypotensive, tracheal deviation, desaturating. Immediate intervention sequence?
CAG in action: the entire ATLS 10th edition, the hospital's trauma bay protocol (v4.2, last updated 3 months ago), the massive transfusion protocol, and the chest tube insertion checklist are already pre-cached in the KV cache. The model answers instantly: "1) Needle decompression 2nd ICS mid-clavicular line. 2) 36Fr chest tube 5th ICS anterior axillary. 3) Activate MTP. 4) If >1500mL blood output, OR for thoracotomy." No retrieval delay. No risk of pulling the wrong guideline.

Why CAG is essential here

  • In trauma, latency kills. A 500ms retrieval delay during a code is unacceptable.
  • The knowledge (ATLS protocols) is highly stable, updated every few years, not every day.
  • The knowledge set is bounded. A few hundred pages fit easily in context.
  • Wrong retrieval could mean the wrong intervention. CAG removes that risk.

Tradeoffs & Risks

✓ Strengths
  • Sub-100ms response times
  • No retrieval errors possible
  • Simpler infrastructure (no vector DB)
  • Deterministic, auditable behavior
  • Lower per-query compute cost
✕ Risks
  • Cache invalidation is hard; an outdated cache gives wrong answers
  • Knowledge must fit in the context window
  • Not suitable for rapidly changing information
  • GPU memory pressure for large caches
  • Rebuild cost when knowledge changes
"CAG is the right answer when your knowledge is small enough, stable enough, and latency-sensitive enough that retrieval overhead is unacceptable."
Section 03 · Memory-Augmented Generation

3MAG: Remember Users Across Time

MAG solves the continuity problem. Standard AI has amnesia. Every conversation starts from zero. MAG gives the AI a persistent, evolving memory of each user: their preferences, their history, their context. It learns over time, which is what makes truly personalized AI possible.

Core Definition

Memory-Augmented Generation (MAG)

An architecture where the AI maintains a persistent, structured memory for each user (patient, clinician, staff). This memory is updated continuously as the user interacts with the system, and it is retrieved and injected into context at inference time. The AI does not just know facts. It knows you.

Interaction → Extract → Update Memory Store → Retrieve at Query → Generate (personalized)

The Memory Lifecycle: Four Critical Operations

① Remember (Write)

Extract salient facts from each interaction and persist them. "Sarah is afraid of needles." "Dr. Smith prefers bullet-point summaries." "Patient X missed the last 3 appointments."

② Retrieve (Read)

At the start of each interaction, pull the user's relevant memories into context. Semantic search over the memory store ensures only pertinent memories surface.

③ Update (Refine)

Memories evolve. When new information contradicts old, the system must resolve the conflict: "Sarah now prefers CGM over finger pricks" overwrites the old needle-phobia-driven memory.

④ Forget (Prune)

Critically, the system must know what to forget: outdated facts, irrelevant trivia, or information the user has explicitly asked to remove. Forgetting matters as much as remembering.

Figure 3.1 · MAG pipeline: a persistent per-user memory store mediates between the user and the LLM, enabling personalization.

Key Characteristics of MAG

Per-User Identity

Each user has their own memory graph. The AI knows "Sarah" differently from "John": different histories, different preferences.

Temporal Evolution

Memories carry timestamps and decay. The AI learns how users change over weeks, months, and years.

Contextual Continuity

Conversations feel continuous, not transactional. The AI picks up where it left off, even across sessions.

Personalized Chronic Disease Coaching

Sarah, 42, Type 2 Diabetes · Post-discharge app · Week 6 of coaching

Sarah was discharged 6 weeks ago after a diabetes-related hospitalization. She uses the hospital's AI-powered chronic care app every day. Over these 6 weeks the AI has built up a rich memory of her:

  • Medical memory: eGFR 52 (stage 3a CKD), A1c 8.4% at discharge, on metformin + empagliflozin
  • Behavioral memory: severe needle phobia (prefers CGM over fingersticks), works night shifts at a hospital (3pm–3am), struggles with carb-counting after 10pm
  • Preference memory: prefers voice messages over text, likes simple recipes, finds long educational videos overwhelming
  • Progress memory: missed 2 medication doses last Tuesday (during a busy shift), walked 4,200 steps on average this week (down from 5,500 last week)
Hi Sarah, how are things going this week?
MAG in action: the AI retrieves Sarah's full memory graph. It knows not to suggest fingerstick checks (needle phobia). It knows she works nights (so "good morning" is wrong at 4pm). It knows her A1c is still elevated but her CGM data shows improvement. It remembers she struggled with carb-counting last week. Response: "Hey Sarah, I noticed your shifts have been hectic this week, and you missed a couple of empagliflozin doses Tuesday. No judgment, nights are tough. I also saw your steps dipped a bit. Want me to send a 10-minute walk reminder between your patient rounds? And I found a 3-ingredient low-carb dinner recipe that takes 15 minutes. Want me to share it?"

Why MAG is essential here

  • Generic diabetes advice fails. Patients need personalized guidance.
  • Continuity builds trust. Sarah feels known, not processed.
  • Behavioral patterns emerge over weeks, not single conversations.
  • The AI can intervene proactively based on memory trends.

The Hard Problems of MAG

Memory is powerful, but it introduces challenges that RAG and CAG do not face:

🧠 What to Remember?

Not every utterance is worth persisting. The system has to decide: is "I like blue" a meaningful preference or noise? That takes sophisticated salience detection.

🗑️ What to Forget?

Outdated memories become wrong. If Sarah's kidney function worsens, dietary advice based on the old eGFR becomes dangerous. Decay functions and explicit user control are essential.

⚖️ Conflict Resolution

When a new memory contradicts an old one, which wins? "I hate running" (month 1) versus "I just finished my first 5K!" (month 6). The system must update, not hold both.

🔒 Privacy & HIPAA

Persistent memory of patient data is a regulatory minefield. Memories must be encrypted, access-controlled, auditable, and deletable on request (right to erasure).

Tradeoffs & Risks

✓ Strengths
  • True personalization at scale
  • Builds user trust and engagement
  • Enables proactive, not just reactive, AI
  • Longitudinal insights impossible in single sessions
  • Compounds in value over time
✕ Risks
  • Privacy and regulatory complexity (HIPAA, GDPR)
  • Memory drift, so stale or wrong personalization
  • Hard to debug ("Why did it say that?")
  • Requires careful salience detection
  • Forgetting is as hard as remembering
"MAG is the right answer when your users return repeatedly, when their context evolves over time, and when generic responses are no longer good enough."

Section 05 · The Hybrid Architecture

The Highest-Performing Systems Combine All Three

The best enterprise hospital AI systems do not pick one architecture. They layer all three. Each handles what it does best, creating a unified "Chief of Staff" experience for clinicians and a deeply personalized experience for patients.

Figure 5.1 · Hybrid architecture: the orchestration layer routes each query to the right combination of RAG, CAG, and MAG, then synthesizes the final response.

Hybrid Workflow 7:45 AM · Before Clinic

Dr. Smith's Morning Chart Review

Dr. Smith opens the AI assistant to review the day's patients. One query triggers all three architectures at once:

Summarize Mrs. Johnson's status and prep me for her 6-month diabetes visit.

① MAG activates first, personalization

  • Retrieves Dr. Smith's style: "bulleted HPI, narrative assessment, no em-dashes"
  • Retrieves Mrs. Johnson's memory: last visit 6 months ago, started semaglutide, A1c 8.1 to 7.3, lost 8 lbs, grandson's wedding coming up
  • Formats the output exactly how Dr. Smith likes it

② CAG handles core knowledge, instantly

  • Current semaglutide dosing rules (cached)
  • Standard diabetes monitoring intervals (cached)

③ RAG retrieves dynamic information

  • Mrs. Johnson's latest labs from yesterday (EHR)
  • Any new ADA guideline updates this month (journals)
  • Her recent pharmacy fill history (dynamic)
  • Any new clinical trials for semaglutide she might qualify for

Result: a perfectly personalized, instantly informed, fully up-to-date chart summary, generated in under 2 seconds, citing sources, formatted exactly how Dr. Smith prefers.

When to Layer: The Decision Heuristic

Add RAG when…

Knowledge changes daily, is massive, or must be cited. Patient-specific data, the latest research, dynamic formularies.

Add CAG when…

Knowledge is stable, bounded, and latency-sensitive. Protocols, rules, and reference material that rarely changes.

Add MAG when…

Users return repeatedly and personalization drives outcomes. Chronic care, workflow tools, therapeutic companions.

Section 06 · Decision Framework

How to Choose: The Right Question

The architecture decision is usually straightforward once you ask the right questions. Stop asking "which is best?" Start asking these three questions instead:

Does the knowledge change daily?
Yes, use RAG.
Examples: patient records, latest journals, drug formularies, clinical trials, regulatory updates. You need retrieval because caching would be constantly stale.
Is the knowledge stable and bounded?
Yes, use CAG.
Examples: ATLS protocols, formulary, ICD codes, hospital policies (updated yearly). You can cache it because it rarely changes, and latency matters.
Do users come back repeatedly?
Yes, use MAG.
Examples: chronic care patients, clinician workflow tools, therapy companions. You need memory because personalization drives outcomes over time.

The Final Insight

Architecture is not about trends.
It's about matching the system design to the problem.

The highest-performing hospital AI systems don't pick one.
They combine RAG for dynamic information,
CAG for core knowledge,
and MAG for user memory.
The Enterprise Playbook

Build the triad. Layer by layer.

Start with CAG for your most latency-sensitive, stable knowledge (protocols, formularies).
Add RAG for everything dynamic (EHR, journals, real-time data).
Layer in MAG for your highest-value, recurring users (chronic patients, power-user clinicians).
The orchestration layer decides, per query, which combination to invoke.
